# Build cards: paged fact slides beside a live workflow video

**Status:** approved 2026-08-12 · **Scope:** `site/` crate and its assets · **Supersedes:** the
single-blurb card introduced in `75585b6`.

---

## Problem

The current build card is one paragraph of text next to a screenshot band. Two things are wrong
with it.

**Wasted space.** The screenshot band is cropped to a fixed height and the text runs to four
lines, so most cards carry a large empty region that says nothing.

**Wasted material.** Each build has a real story — a measured number, a mechanism, a failure
found in production, a stated limit — and none of it is on the landing page. It lives in the
cycle READMEs, one click away, which most visitors never take.

## Constraints

- Static output. The site is generated by `site/` (Dioxus SSR → one HTML file) and served from
  GitHub Pages under `/pursuit-l2-portfolio/`. No server, no framework runtime.
- A portfolio gets roughly fifteen seconds. **Nothing essential may sit behind a click.**
- Each card keeps its own project theme: surface, accent, chip, display face. That decision
  stands and is enforced by const assertions in `site/src/theme.rs`.
- Prefer less vertical scrolling. Depth should move sideways, not down.

## Design

### Card anatomy

Each card is a fixed-height frame containing a **media slot** sized to that app's real shape and
a **slide panel** occupying everything else. No empty region remains.

```
portrait build (HouseCheck, SiteAssure, Resona)      landscape build (Ziqpu)
┌───────────────────────────────────────┐            ┌───────────────────────────────────────┐
│  ┌────────┐  Ziqpu-style title        │            │  ┌─────────────────────────────────┐  │
│  │        │  ── slide 1 of 4 ──       │            │  │                                 │  │
│  │ phone  │                           │            │  │            video                │  │
│  │ bezel  │  claim + hardest number   │            │  │                                 │  │
│  │        │                           │            │  └─────────────────────────────────┘  │
│  │ video  │  tags                     │            │  title · slide 1 of 4                 │
│  │        │                           │            │  claim + hardest number · tags        │
│  └────────┘  ● ○ ○ ○      ‹  ›        │            │  ● ○ ○ ○                     ‹  ›    │
└───────────────────────────────────────┘            └───────────────────────────────────────┘
```

**Device treatment.** A thin rounded bezel drawn in the card's own `--edge`, 1 px, radius 10 px.
Not a photoreal phone body — skeuomorphic device mockups are a template signal. The bezel exists
only to make the portrait aspect read as deliberate.

### Slides

Four per build. **Slide 1 is load-bearing and must stand alone**; slides 2–4 are depth that
rewards a reader who chooses to go further.

| # | Title | Carries |
|---|---|---|
| 1 | What it is | The one-line claim, the hardest measured number, the tags |
| 2 | How it works | The mechanism, three bullets |
| 3 | The hard part | The genuinely difficult or surprising thing |
| 4 | What it doesn't do | The stated limit |

Slide 4 is not a disclaimer section. It is the same honesty the builds themselves practise, and
it belongs on the card for the same reason the cards state contrast ratios.

### Progressive enhancement — the load-bearing mechanic

**The HTML contains all four slides, rendered stacked and visible.** A small inline script
collapses them into a pager on load.

This ordering is deliberate and non-negotiable:

- Crawlers, screen readers with scripting off, Reader modes and print all get the full text.
- A JS error degrades to a longer page, never to a blank card.
- The pager is an enhancement. The document is the source of truth.

The script adds `data-paged` to `.builds`; all pager CSS is scoped under that attribute, so with
no JS none of it applies.

### Interaction

- Prev/next are real `<button>` elements with `aria-label`; dots are buttons with
  `aria-current="true"` on the active slide.
- The slide region is `aria-live="polite"` so a screen reader announces a change.
- `←` / `→` page when focus is inside a card. They must not hijack the arrow keys globally.
- Focus ring: 2 px `--accent`, offset 3 px — matching the existing card focus style.
- The card remains a link to its cycle README. Pager controls call `preventDefault()` and
  `stopPropagation()` so paging never navigates away. **This is the main correctness risk in the
  feature** and needs an explicit test.

### Motion

- `<video autoplay muted loop playsinline preload="metadata">` with a `poster`.
- Under `prefers-reduced-motion: reduce` the video is not autoplayed; the poster frame shows and
  a control appears. Slides never auto-advance under any setting.

### Theme

Unchanged. The slide panel uses `--card-ink` / `--card-ink-2`; dots and the active indicator use
`--accent`; the bezel uses `--edge`. No new theme fields except those listed below.

## Data model

In `site/src/content.rs`, extending the existing `Build`:

```rust
pub struct Slide {
    pub title: &'static str,
    pub lead: &'static str,
    pub points: &'static [&'static str],   // empty for slide 1
}

// added to Build:
pub slides: &'static [Slide],   // exactly 4, enforced by a test
pub media: Media,
pub poster: &'static str,

pub enum Media { Portrait, Landscape }
```

`Media` decides the slot shape, so a fifth build declares its shape rather than the layout
guessing from a filename.

## Testing

- `every_build_has_four_slides` — the pager assumes four; a three-slide build would render a
  dead dot.
- `slide_one_is_self_contained` — slide 1's `lead` is non-empty and its `points` are empty, so
  the load-bearing slide cannot silently become a bullet list that depends on slides 2–4.
- `media_matches_asset` — each build's declared `Media` matches the recorded video's actual
  aspect, so a re-recorded asset that changes shape fails the build rather than the layout.
- The existing const contrast assertions continue to cover every theme.
- Manual: with JS disabled every slide is visible; with JS enabled clicking a pager control does
  not navigate to the linked README.

- Any generated video. Every frame on this site is a recording of the real application.
